# Demo: an interactive ForgeCI self-hosting run

This five-minute walkthrough uses an isolated PostgreSQL container, a real
ForgeCI server, and two real runner processes. The environment stays running
until explicitly stopped. It submits only source archived from committed
`HEAD`; untracked files, `.git`, build output, and demo logs are excluded.

## Preparation

Use a Linux host with Git, Go 1.27 or newer, Docker, `curl`, `tar`, and `jq`.
Start Docker and pre-pull the two images so downloads do not interrupt the
walkthrough:

```bash
docker pull postgres:17-alpine
docker pull alpine:3.20
./tools/demo/run.sh
```

The last command prints the loopback server URL. Keep that terminal visible;
the setup logs are written to the isolated runtime directory instead of mixed
into the presentation. The environment starts healthy but submits no work.

## 1. Show both runners

```bash
./tools/demo/status.sh
SERVER=$(sed -n 's/^FORGECI_SELF_SERVER=//p' .forgeci-demo/state)
./build/forge runners --server "$SERVER"
```

The status command queries the PostgreSQL container, server health endpoint,
and runner API. It should report PostgreSQL and the server as `READY`, with
`runner-a` and `runner-b` both `ONLINE`.

## 2. Submit the real self-hosting DAG

Open [`forge.yaml`](../forge.yaml), then submit that exact file from the
committed-source workspace:

```bash
RUN_ID=$(./build/forge submit --quiet --server "$SERVER" --file forge.yaml --jobs 4)
printf 'RUN_ID=%s\n' "$RUN_ID"
./build/forge wait "$RUN_ID" --server "$SERVER" --timeout 15m
```

Runner capacity is one job per process. The independent root jobs give the real
scheduler concurrent eligible work; ownership is not assigned by the demo.

## 3. Inspect durable run state

```bash
./build/forge inspect "$RUN_ID" --server "$SERVER"
```

The output contains the real run ID, terminal state, pipeline digest, source
digest, every job state, and runner identities. The runner identities are
generated by registration; `tools/demo/capture.sh` joins them to the observed
runner names in its evidence summary.

## 4. Retrieve durable stdout and stderr

```bash
./build/forge logs "$RUN_ID" --job docker-smoke --server "$SERVER"
```

The committed job writes `forgeci-docker-smoke-stdout` to stdout and
`forgeci-docker-smoke-stderr` to stderr. Their retrieval after completion proves
that log chunks were persisted and read through the control plane.

## 5. Capture artifact and cache proof

For the assertion-backed sequence, start with a fresh environment and run the
shared proof script:

```bash
./tools/demo/stop.sh
./tools/demo/run.sh
./tools/demo/capture.sh demo-evidence/candidate
```

The capture submits `forge.yaml` twice. It downloads `self-binaries`, extracts
the archive, and verifies `forge`, `forge-server`, `forge-runner`, and the build
marker. It then verifies that unchanged committed source has the same snapshot
digest and that cache access metadata advances. It does not claim a performance
gain or hit ratio.

## 6. Show deterministic failure semantics

The same capture submits the committed
[`self_host_failure.yaml`](../tools/integration/fixtures/self_host_failure.yaml)
and records:

```text
independent-pass     PASSED
intentional-fail     FAILED
blocked-dependent    BLOCKED
```

It also retrieves the persisted `forgeci-intentional-failure` marker from the
failed job. No ad hoc failure or runner crash is used during the demo.

## 7. Review captured evidence

The candidate directory contains `summary.json`, raw CLI inspection, named job
placement, runner state, artifact listing, durable logs, failure output, and a
SHA-256 manifest. Values are observed or asserted by the same proof driver used
by `tools/integration/self_hosting.sh`; credentials, personal paths, ports,
hostnames, binaries, and database state are excluded.

The public showcase presents one reviewed capture as static evidence. It never
labels the capture live.

## 8. Explain the exact-revision boundary

The local demo proves committed-source isolation. Native GitHub exact-revision
behavior remains covered by [`github-scm.md`](github-scm.md), the
[`materialize` tests](../internal/scm/git/materialize_test.go), and the
[`mutation matrix`](../tools/integration/m12_mutations.sh). The main walkthrough
does not require GitHub App credentials or fake a webhook.

## 9. Stop cleanly

```bash
./tools/demo/stop.sh
```

The stop command validates the state file, process command lines, temporary
root, and Docker ownership label before removing only the recorded environment.
If startup is interrupted, `run.sh` cleans up partial resources and prints a
failure message. Once startup completes, the explicit stop command is always
shown in its output.
