# Demo: ForgeCI runs ForgeCI

This is a deterministic 5–10 minute walkthrough of the evidence ForgeCI
already produces. It uses the repository's real self-hosting pipeline and
integration harness; it does not simulate a dashboard or depend on a hosted
ForgeCI environment.

The complete harness builds three bootstrap binaries, starts an isolated
PostgreSQL container, a ForgeCI server, and two real runner processes. It then
submits the root `forge.yaml` twice, verifies artifacts and cache reuse, and
submits an intentional-failure fixture. Everything is removed when the harness
exits.

## Before the walkthrough

Use a Linux host with Git, Go, Docker, `curl`, and PostgreSQL's container image
already available. Docker must be running. To avoid spending the walkthrough on
downloads or compilation, run this once beforehand from the repository root:

```bash
go test ./...
./tools/integration/self_hosting.sh
```

The second command is the proof itself, so keep its successful output available
for the walkthrough. It prints real run IDs, source digests, runner placement,
cache access timestamps, and the published artifact name. Those values are
generated by that execution and are intentionally not copied into this guide.

## 1. Establish the execution model

Open [`architecture.png`](../architecture.png) and explain the boundaries:

```text
GitHub SCM / CLI
        ↓
ForgeCI control plane + PostgreSQL
        ↓
fenced job leases
        ↓
remote runners
        ↓
source / artifacts / cache / logs
```

GitHub-specific webhook, authentication, source-fetch, and Check logic lives at
the SCM boundary. The control plane and runner protocol operate on generic runs,
jobs, snapshots, leases, artifacts, caches, and logs.

## 2. Read the self-hosting DAG

Open the root [`forge.yaml`](../forge.yaml). Point out that `format`, `vet`, and
`unit` are independent roots; `race` follows `unit`; `build` waits for all three
root jobs; and `binary-smoke` and `docker-smoke` both restore the artifact
published by `build`.

This is the exact pipeline submitted by the harness, not a demo-only fixture.

## 3. Run or replay the self-hosting proof

If the host is prepared and the time budget allows, run:

```bash
./tools/integration/self_hosting.sh
```

Otherwise, use the output captured during preparation and walk through the
checks in [`tools/integration/self_hosting.sh`](../tools/integration/self_hosting.sh).
The harness itself is the authoritative, executable record.

The harness performs these steps without requiring manual IDs or secrets:

1. Archives committed `HEAD` into an isolated source directory.
2. Starts PostgreSQL, `forge-server`, and two `forge-runner` processes.
3. Waits until both runners report `ONLINE`.
4. Submits the real `forge.yaml` with bounded parallelism.
5. Waits for the run and inspects every job result.

## 4. Show real distribution and durable state

In the harness output, use the `JOB / RUNNER` table and `Distinct runners` line
to show that jobs were placed on both runner processes. Then connect those
values to the commands the harness actually executes:

```bash
forge runners --server "$server"
forge inspect "$run" --server "$server"
forge logs "$run" --job docker-smoke --server "$server"
```

`inspect` shows the pipeline and source SHA-256 identities plus job-to-runner
placement. The log check retrieves persisted stdout and stderr through the
control plane. The shell variables above belong to the harness; they are shown
to explain its calls, not as standalone commands for a cleaned-up environment.

## 5. Show artifact restoration and cache reuse

Follow the corresponding assertions in the harness:

- `build` publishes the `self-binaries` artifact.
- both smoke jobs declare restoration of that artifact in `forge.yaml`.
- the harness downloads the stored archive and verifies all three binaries and
  the build marker.
- a second unchanged submission has the same source snapshot digest.
- the named unit-test cache remains present and its access time advances.

This demonstrates explicit cross-runner transport and reuse without claiming a
cache ratio, duration, or performance number.

## 6. Show failure semantics

The harness submits
[`tools/integration/fixtures/self_host_failure.yaml`](../tools/integration/fixtures/self_host_failure.yaml)
and verifies three distinct outcomes:

- an independent job passes;
- the intentionally failing job fails;
- its dependent job is blocked.

It then retrieves the failing job's durable log. No failure needs to be
improvised during the walkthrough.

## 7. Finish with exact-revision and SCM evidence

The local self-hosting harness starts at committed source, while native GitHub
SCM additionally proves that an event's exact revision survives a moving branch:

- [`docs/github-scm.md`](github-scm.md) documents signed webhook ingestion,
  exact fetch and detached checkout, durable delivery processing, and Checks.
- [`internal/scm/git/materialize_test.go`](../internal/scm/git/materialize_test.go)
  creates multiple revisions and verifies the requested SHA is checked out.
- [`tools/integration/m12_mutations.sh`](../tools/integration/m12_mutations.sh)
  deliberately weakens exact checkout, lease fencing, transactional trigger
  creation, and Check adoption, then requires the targeted tests to fail.

The conclusion is precise: GitHub Actions currently supplies the outer Linux
host for the dogfood workflow; ForgeCI parses, schedules, distributes, stores,
and evaluates the project DAG.

## Phase 2 improvement

The current harness is optimized as an all-or-nothing integration proof and
cleans up on exit. A later demo-specific harness can add a safe pause or
read-only attach mode so an operator can issue `runners`, `inspect`, `logs`,
artifact, and cache commands interactively against the still-running isolated
stack. That interactive harness does not exist yet and is not assumed here.
